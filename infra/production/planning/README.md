# Домен, HTTPS и внешняя почта: подготовка DIMAX

Статус на 23 октября 2026: **план, не развёртывание**. Реального домена,
сервера и SMTP-провайдера пока нет. Рабочие данные и настройки не меняем.

## Что подготовлено

`public-services.example.ini` фиксирует согласованные между компонентами адреса.
Это справочник, а не исполняемый конфиг: приложение и deploy.sh его не читают.
Не копировать целиком в .env, не подключать к Compose, не отправлять ссылки
на эти адреса представителям завода. `.example` используется только как пример.

| Назначение | Черновой адрес | Куда затем перенести реальное значение |
|---|---|---|
| Админка | https://ops.dimax.example | edge DIMAX_ADMIN_HOST; backend PUBLIC_APP_BASE_URL и CORS_ALLOW_ORIGINS |
| API и публичные ссылки | https://api.dimax.example | edge DIMAX_API_HOST; backend PUBLIC_BASE_URL |
| API для сборки админки | https://api.dimax.example | NEXT_PUBLIC_API_BASE_URL |
| API для сборки телефона | https://api.dimax.example | EXPO_PUBLIC_API_BASE_URL |
| Отправитель | notifications@dimax.example | backend SMTP_FROM, после проверки домена провайдером |
| SMTP | smtp.dimax.example:587 | заменить на точный сервер провайдера с STARTTLS |
| Контакт TLS | infrastructure@dimax.example | DIMAX_TLS_EMAIL: нужен реально обслуживаемый ящик |

SMTP-хост не обязан находиться в домене DIMAX. Не создавать для него произвольный
CNAME: использовать имя из настроек провайдера, которому соответствует сертификат.
Текущий отправитель использует STARTTLS, а не implicit TLS/SMTP_SSL на порту 465.
Исправление проверки сертификата находится в backend, коммит
`be971d6afcaaa25eac49c2e0e83042b79842ad4f`; при сборке убедиться, что оно включено.

## Что потребуется от владельца

1. Купить домен и указать, где управляется DNS. Сейчас ничего не покупаем.
2. Выбрать сервер/провайдера, получить адрес сервера и разрешение на отдельный staging.
3. Выбрать SMTP-сервис с STARTTLS, подтвердить домен отправителя, получить его DNS-записи.
4. Указать контролируемые адреса для тестовой доставки и контакта TLS.
5. Передать доступы через защищённое хранилище/настройки сервера, не через чат или Git.

SMTP_USER, SMTP_PASSWORD, FACTORY_APPROVAL_EMAIL_KEY и JWT_SECRET намеренно
отсутствуют в черновике. Ключи не создавать и не менять в рабочем окружении.
Для staging использовать отдельные ключи, базу, хранилище и тестовые контакты.

## Порядок следующей реальной проверки

1. **Отдельный staging.** Выделить отдельные имена, например ops-staging и api-staging
   уже купленного домена. Не подключать рабочую БД, её копии с персональными данными
   или рабочую очередь писем. Использовать только синтетический объект и договор.
2. **DNS.** Направить A-записи этих имён на staging-сервер. AAAA добавлять только
   при реально работающем IPv6. Значения SPF/DKIM и проверки домена взять у почтового
   провайдера; политику DMARC согласовать отдельно. Не выдумывать ключи, селекторы
   и готовые DNS-записи. MX нужен согласно выбранной схеме приёма почты, а не как
   автоматическое условие работы SMTP-отправителя.
3. **Настройки.** Заполнить существующие production-шаблоны для staging отдельно
   от локальных .env. Сверить адреса по таблице. Разрешить в CORS только origin
   этой админки. SMTP_TLS=true, SMTP_PORT=587, EMAIL_ENABLED=true; API и outbox-worker
   должны иметь одинаковые настройки почты и ключ подтверждения.
4. **Сборки.** Собрать backend с проверкой SMTP-сертификата, админку и телефон
   с нужными публичными API URL. Изменение переменной после сборки не считать
   обновлением уже выпущенного клиента. Использовать неизменяемые версии образов.
5. **Preflight.** На отдельном сервере выполнить существующий deploy.sh --check.
   Он не доказывает доступность DNS/HTTPS/SMTP. Выдуманные адреса должны отклоняться;
   не ослаблять валидатор ради зелёного результата. Сам deploy.sh без --check
   применяет миграции: запускать его только для явно проверенного staging.
6. **HTTPS.** Воспользоваться существующим Caddyfile, открыв серверу необходимые
   80/443 и сохранив тома Caddy. Проверить оба имени, цепочку доверия, срок сертификата
   и перенаправление HTTP в HTTPS из внешнего браузера. Не обходить ошибки сертификата,
   не устанавливать локальный CA на телефон ради имитации рабочего HTTPS.
7. **Почта.** Отправить одно синтетическое приглашение только в разрешённый тестовый
   ящик. Проверить получение, отправителя, SPF/DKIM/DMARC по заголовкам и корректный
   HTTPS-адрес в письме. Принятие SMTP-сервером не равно доставке. Зафиксировать
   отказ/повторную попытку в outbox при ошибке, без повторного подтверждения расчёта.
8. **Бизнес-цепочка.** OWNER утверждает тестовый контакт завода; уполномоченный
   админ отправляет конкретную версию условий и прайса. Представитель открывает
   ссылку, получает код в свой ящик и подтверждает именно эту версию. Проверить
   защиту от повторного решения, истёкшей ссылки, чужой компании и подмены версии.
   Подтверждение не должно само менять активный прайс или начислять деньги:
   отдельная активация админом сохраняется.
9. **PDF.** На отдельном тестовом журнале проверить письмо с читаемым PDF для
   назначенных тестовых адресатов. Представитель объекта подписывает объёмы без цен;
   коммерческий расчёт заводу отделён от ставок монтажника. Не смешивать эту
   проверку с подтверждением коммерческого прайса.
10. **Приёмка.** Зафиксировать версии, время проверки, сертификаты, результат
    доставки и бизнес-цепочки. Удалить из публикуемых материалов токены, коды,
    пароли, адреса участников и содержимое клиентских документов. Только затем
    отдельно согласовать переход на реальные данные, резервирование и восстановление.

## Что можно проверить прямо сейчас

Из корня workspace, без Docker, DNS-запросов, внешних писем и записи в БД:

```powershell
python -B -m unittest discover -s infra/production/tests -v
node --test scripts/production-infra-contract.test.mjs
```

Тесты planning проверяют согласованность адресов, STARTTLS и отсутствие секретов
в справочнике, а также отказ существующего preflight принимать этот выдуманный
домен. На Windows shell-тесты Linux пропускаются, это нужно отметить в отчёте.
Эти проверки не выдают публичный сертификат и не подтверждают внешнюю доставку.
